Q5

大会幸运抽奖应用

练习模式 · 不限次数 · 提交后由大模型自动评分，达到 70 分即算通过

题目交付物随题材料提交答卷

一、业务背景

公司年度客户大会在酒店宴会厅举行，到场约 300 人（客户 + 员工），签到已经通过微信小程序完成，会务组把签到结果导出成名单。大会尾声是幸运抽奖环节，奖品分 4 档共 15 个名额。

现在的抽奖方式是**"抽奖箱 + Excel 随机排序"**，问题很多：

  • 现场没有大屏，中奖名单只能靠主持人念，台下看不清，体验差；
  • 用 RAND() 排序抽出来的名单，事后无法自证公平——客户会私下问"是不是内定的"；
  • 工作人员手工登记中奖名单，重复中奖、漏记时有发生；
  • 有工作人员混在参与池里被抽中（工作人员不应参与抽奖）；
  • 签到名单里有重复签到、手机号写错、工作人员代签等脏数据，直接拿来抽会造成"人数对不上";
  • 会后要整理中奖名单，还要手工核对，很费时间。

市场部希望做一个抽奖应用：参与池直接来自已签到名单（清洗后），会场大屏实时展示，工作人员用手机打开控制台发起抽奖，抽奖过程与结果可审计（能向客户证明没有内定），并且任何一个人都只能中一次奖。

二、任务目标

做一个基于签到名单的大会抽奖应用：正确构建参与池 → 大屏展示 → 控制台发起抽奖 → 结果落库且可复算 → 同一人绝不重复中奖。

三、功能需求

编号需求验收要点
FR-1参与池构建从 已签到名单.csv 构建参与池，按下方「清洗规则」执行；启动日志给出清洗统计与告警
FR-2奖项配置读取 奖项配置.csv（奖项名、名额、顺序），4 个奖项共 15 个名额
FR-3抽奖工作人员发起抽奖时，一次性抽满该奖项的全部名额；随机数必须由服务端生成
FR-4跨奖项排重已中奖者不再进入后续奖项的抽奖池；任何奖项间都不得重复中奖（数据库层需有兜底约束）
FR-5幂等与并发该奖项名额抽完后再次抽奖返回 409；并发发起两次抽奖只能有一次成功（不能抽出双份中奖者）
FR-6可审计（可复算）每次抽奖记录：随机种子、参与池规模与快照 hash、算法说明、中奖名单、抽奖时间；提供审计查询接口与复算校验接口（用记录的种子重算，验证与已公布名单一致）
FR-7大屏展示公开页面：参与池人数、已抽出/总名额、各奖项与其中奖名单；自动刷新（≤10 秒），字号适配投屏
FR-8工作人员控制台口令保护；可看到参与池清洗统计（各排除项数量）并发起抽奖
FR-9隐私保护中奖名单可公开展示，但必须手机号脱敏；完整参与池与审计信息需口令，未授权访问返回 401
FR-10数据持久化名单、奖项状态、中奖记录、审计信息全部落盘；重启后中奖记录仍在、不能重复抽奖
FR-11一键启动与文档一条命令启动；README 写清依赖、启动命令、大屏地址、控制台地址与口令、数据存储位置

参与池清洗规则（FR-1 明细，必须按此执行）

情况处理方式
角色为工作人员不参与抽奖，排除（不计入参与池）
角色不是"客户"或"员工"（含角色为空）无法确认身份，排除，并在日志中告警
手机号经归一化后不是 11 位 / 不以 1 开头无法识别个人，排除，并在日志中告警
同一手机号出现多条签到记录视为同一人重复签到，只计一次（保留首次签到），并在日志中告警
手机号写法不统一（空格、横线、+86/86 前缀、全角数字）归一化后视为同一人
姓名/公司前后有空格或全角空白统一去除首尾空白

参与池人数由上述规则唯一确定；请在你的报告/日志中说明清洗结果（共多少行、排除了多少、参与池多少人）。

四、技术要求与约束

编号约束
TR-1必须能在普通笔记本上运行；不得依赖云服务、外部数据库、需要注册的第三方 API
TR-2服务需监听 0.0.0.0（或等价局域网可达地址），使大屏机器与工作人员手机都能访问；不要求域名与 HTTPS
TR-3必须提供依赖清单与一条命令启动的方式
TR-4数据不得只保存在内存；重启后中奖记录、审计信息与名额状态必须一致
TR-5随机数必须由服务端生成；不得采信客户端提交的中奖名单/种子；不得使用可预测的伪随机（如以时间戳为唯一种子）
TR-6抽奖结果必须可复算验证：记录足够信息，第三方能用同一种子与同一参与池复现相同名单
TR-7工作人员接口必须口令校验；公开接口不得泄露完整手机号
TR-8代码结构清晰（路由/业务/存储分层）、关键逻辑有注释、异常有处理、有运行日志
