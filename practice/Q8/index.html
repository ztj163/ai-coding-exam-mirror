Q8

订单收款对账（CSV 对账 · 多表关联）

练习模式 · 不限次数 · 提交后由大模型自动评分，达到 70 分即算通过

题目交付物随题材料提交答卷

一、业务背景

财务每月要做订单收款对账：把「订单明细」（应收）和「收款流水」（实收）两张表对起来，算出每笔订单实收了多少、还差多少、对账状态如何。

目前财务是用 Excel 手工 VLOOKUP + 透视表，问题很多：

  • 订单明细里的金额有时是脏数据（abc、NaN、空、12.50、-100、+100、带前导零与空格）；
  • 收款流水里 FAILED / PENDING 的收款不能算实收，但手工筛选经常漏掉；
  • 同一笔收款被导出两次（完全重复的行），手工做透视会重复计入；
  • 有的收款对应的订单已经取消、或者订单号根本不存在（流水串号）；
  • 订单号大小写不一致（o1001 与 O1001 实际是同一笔订单）；
  • 一笔订单可能分多次收款；
  • 有的订单实收超过应收（多收），手工对账时容易被当成正数差异忽略掉。

财务需要一个命令行工具：输入两张 CSV，输出一张对账结果表，口径固定、可复核、可重复执行。

二、任务

编写 Python 程序，通过命令行执行：

Bash python main.py orders.csv payments.csv reconciliation.csv

  • 参数 1：订单明细 CSV（orders.csv）
  • 参数 2：收款流水 CSV（payments.csv）
  • 参数 3：对账结果输出路径（reconciliation.csv）
  • 程序需按下方口径计算，并输出每笔有效订单一行的对账结果表

三、输入说明

3.1 orders.csv（订单明细）

列名含义说明
order_id订单号可能有首尾空白
customer_name客户名称可能有首尾空白；可能含逗号/引号（CSV 已正确转义）
order_amount_cents订单金额（分）可能是不合法内容（见 5.1）
status订单状态COMPLETED（已完成）/ CANCELLED（已取消）；可能有首尾空白

3.2 payments.csv（收款流水）

列名含义说明
payment_id收款凭证号可能为空；可能有首尾空白
order_id对应订单号可能有首尾空白、大小写可能不一致；可能为空
paid_amount_cents收款金额（分）可能是不合法内容
status收款状态SUCCESS（成功）/ FAILED（失败）/ PENDING（处理中）；可能有首尾空白

两份文件都是 UTF-8，可能带 BOM；金额单位统一为分，不涉及小数。

四、输出契约

输出 reconciliation.csv：每笔有效订单一行，包含以下 6 列（列名必须完全一致）：

列名类型含义
order_id文本订单号（去首尾空白后的原文）
customer_name文本客户名称（去首尾空白）
order_amount_cents整数订单金额（分）
received_amount_cents整数该订单的实际收款金额（所有有效收款之和）
unreceived_amount_cents整数未收款金额（见 5.5）
reconcile_status文本对账状态，取值只能是 已结清 / 部分收款 / 未收款 / 多收

硬性要求：

  1. 只输出有效订单（见 5.1）：已取消订单、金额无效的订单不出现在结果中；
  2. 按 order_id 升序排列；
  3. 金额列必须是十进制整数字符串（如 750），不能出现小数、货币符号、千分位；
  4. 输出编码 UTF-8（带 BOM 或不带均可，判分会自动兼容）；
  5. 表头必须是上述 6 个列名，不多不少。

示例

orders.csv：

Plain Text order_id,customer_name,order_amount_cents,status O1,甲公司,10000,COMPLETED O2,乙公司,20000, COMPLETED O3,丙公司,abc,COMPLETED O4,丁公司,30000,CANCELLED

payments.csv：

Plain Text payment_id,order_id,paid_amount_cents,status P1,O1,6000,SUCCESS P2,O1,4000,SUCCESS P3,o2,5000,SUCCESS P4,O2,25000,SUCCESS P5,O3,1000,SUCCESS P6,O4,5000,SUCCESS P7,O2,18000,FAILED

输出 reconciliation.csv（有效订单只有 O1、O2）：

Plain Text order_id,customer_name,order_amount_cents,received_amount_cents,unreceived_amount_cents,reconcile_status O1,甲公司,10000,10000,0,已结清 O2,乙公司,20000,30000,0,多收

说明：P3 的 o2 与 O2 是同一订单；P7 是 FAILED 不计入；P5/P6 对应的订单无效或已取消，不计入任何订单。

五、判定规则（必须严格执行）

5.1 有效订单

一条订单记录同时满足以下三条才属于有效订单，否则不输出：

  1. order_id 去首尾空白后非空；
  2. status 去首尾空白后恰好等于 COMPLETED；
  3. order_amount_cents 去首尾空白后是半角非负整数（^[0-9]+$）：
订单金额原值是否有效订单
12000、0、007（=7）、" 00072931 "✅ 有效（按十进制解析）
abc、NaN、null、空❌ 无效
-100、+100❌ 无效（正负号不接受）
12.50、1e3、一千❌ 无效

5.2 有效收款

一条收款记录同时满足以下四条才算有效收款：

  1. status 去首尾空白后恰好等于 SUCCESS（FAILED、PENDING 一律不计）；
  2. payment_id 去首尾空白后非空（无凭证号的流水无法核对，不计入）；
  3. paid_amount_cents 去首尾空白后是半角非负整数（0 有效，规则同 5.1）；
  4. 其 order_id（去首尾空白 + 转大写）能匹配到一笔有效订单。

不满足第 4 条的收款属于未匹配收款（订单不存在 / 订单已取消 / 订单金额无效 / 订单号为空），不计入任何订单的实收。

5.3 重复收款去重

归一化后 (payment_id, order_id, 收款金额) 完全相同的记录视为重复，只计一次（保留首次出现），其余计入剔除。

  • 归一化 = 各字段去首尾空白、order_id 转大写、金额按整数比较（16998 与 00016998 视为相同）；
  • 同一 payment_id 但金额不同（或订单不同）的记录不是重复，都要计入（分笔收款）。

5.4 匹配规则

  • order_id 匹配不区分大小写（o1001 与 O1001 是同一订单）；
  • 一笔订单可以对应多笔有效收款，实收为这些收款金额之和。

5.5 金额计算

  • received_amount_cents = 该订单所有有效收款金额之和（无收款则为 0）；
  • unreceived_amount_cents = max(订单金额 − 实收金额, 0)（多收时未收记为 0，不出现负数）。

5.6 对账状态

按下述顺序判定（先判多收）：

条件reconcile_status
实收 > 订单金额多收
实收 == 订单金额已结清
实收 == 0未收款
其余（0 < 实收 < 订单金额）部分收款

注意：订单金额为 0 且无收款的订单属于已结清（0 == 0）；订单金额为 0 但有收款属于多收。

5.7 其他约定

  • 空行（整行都没有内容）跳过；
  • customer_name 输出去首尾空白后的值；
  • 订单号在随题数据中唯一；如出现重复订单号，可自行采用合理策略并在 README 说明。

5.8 错误处理

以下情况必须报错退出（退出码非 0，错误信息写到 stderr）：

  • 命令行参数个数不对（不足 3 个或多余）；
  • 任一输入文件不存在或不可读；
  • 输入 CSV 缺少必需列（orders.csv 需 4 列齐全，payments.csv 需 4 列齐全）。

附录 B：注意事项

  1. FAILED / PENDING 不能计入实收（最常见的错）；
  2. 重复收款要按"归一化后的凭证号 + 订单号 + 金额"去重——注意 16998 与 00016998 是同一笔；

  5. 未匹配收款（订单已取消/不存在）不要强行挂到某笔订单上；
  6. 未收金额不能为负（多收时记 0），并单独用"多收"状态体现；
  7. 金额必须用整数，不要用 float（12.50 这类脏值也提醒不要用浮点宽松解析）；
  8. 已取消订单与金额无效订单不能出现在输出里（行数会比输入少）；
  9. 客户名要去首尾空白；含逗号/引号的名字写回 CSV 时要正确转义（用标准库即可）；
  10. 缺列时要报错退出，不要静默输出空结果。
